**Official supported Sites editing workflow:** owner/editor opens the existing Site in ChatGPT Sites or its creation chat, describes edits, reviews the updated preview, then explicitly deploys. See [Creating and using ChatGPT Sites](https://help.openai.com/en/articles/20001339-creating-and-using-chatgpt-sites). The current published documentation describes site scheduling and exporting code on request, but does **not** document a GitHub Pages source-to-Sites auto-deploy binding or public deployment REST API. Absence from public docs is not proof that a private capability cannot exist. We do **not** have an authenticated Sites deployment action in this automation; therefore automatic synchronization is **not configured**.

**Safe path:** keep all code in this GitHub branch and its tested GitHub Pages release; if editing the existing ChatGPT Site with authorized Sites Work/Codex, import/reference this exact branch and use its code (not an independent rewrite), inspect preview vs screenshots 01–08 and test touch/ballistics, then publish through Sites and compare both addresses and release stamps. Do not redirect or change the ChatGPT Sites hostname, embed the Pages app without verifying framing/CSP/service-worker behaviour, paste credentials, create an unapproved new Site, or claim the two deployments auto-sync. A static link from the old Sites page to the canonical Pages URL is a simple fallback, but it is **not** synchronization.

**Read-only HTTP probe:** the GitHub Pages verify workflow logs the existing ChatGPT Sites response code if publicly reachable; that probe never deploys or edits Sites. A successful HTTP response alone does not demonstrate version equality, functional equality, access authorization or automation.
